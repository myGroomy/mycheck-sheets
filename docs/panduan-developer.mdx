# Panduan Developer

Panduan onboarding untuk developer yang melanjutkan checklist-shift. Baca
bersama spesifikasi di root repository; panduan ini merangkum struktur dan
perilaku implementasi yang ada, bukan menggantikan spesifikasi.

## Mulai dari dokumen acuan

Urutan prioritas dan aturan kerja berada di `AGENTS.md`. Dokumen lain:

1. `PRD.md` — perilaku produk dan aturan bisnis.
2. `DATABASE_SCHEMA.md` — skema PostgreSQL.
3. `TRD.md` — keputusan arsitektur dan teknis.
4. `APP_FLOW.md` — layar dan alur UX.
5. `IMPLEMENTATION_PLAN.md` — tahapan implementasi.
6. `TESTING.md` — kriteria verifikasi.
7. `UI-UX.md` — panduan visual dan responsif.

Spesifikasi saat ini memuat sejumlah layar dan pekerjaan berstatus rencana.
Sebelum melanjutkannya, periksa route, handler, schema, dan tes yang benar-benar
ada. Jika dokumen bertentangan dengan implementasi atau instruksi kerja,
hentikan perubahan terkait dan minta keputusan; jangan menyimpulkan sendiri.

## Arsitektur dan struktur repository

Monorepo menggunakan npm workspaces:

```text
apps/web/
  app/                 Next.js App Router pages, layouts, dan API routes
  components/          UI petugas, admin, incident, report, dan komponen bersama
  lib/                 autentikasi, database, storage, waktu, audit, dan helper
  drizzle/
    schema.ts          skema Drizzle yang dipakai aplikasi
    migrations/        migrasi database
    seed.ts            seed awal legacy; hanya untuk konteks lokal yang aman
    seed-realistic-demo.ts  fixture demo multi-cabang; cek isi/efek sebelum jalan
  public/              aset PWA
packages/shared/
  src/                 tipe dan validasi Zod bersama
docs/                  panduan MDX sumber; belum menjadi halaman aplikasi
```

Tidak ada `apps/api` atau service API terpisah. API berada pada
`apps/web/app/api/**/route.ts`. Data browser melewati Next.js server/API; akses
langsung browser ke PostgreSQL atau Supabase service-role tidak diperbolehkan.

### Bagian implementasi penting

| Area | Lokasi utama |

## Setup lokal

Gunakan Node.js yang kompatibel dengan Next.js 14 dan npm:

```bash
npm install
npm run dev
```

Aplikasi web berjalan pada port 3000 secara default. Siapkan environment lokal
terlebih dahulu; jangan menaruh nilai rahasia di source code, issue, log,
screenshot, atau file yang dikomit.

Environment yang digunakan kode:

| Variabel | Pemakaian |
| --- | --- |
| `DATABASE_URL` | Wajib untuk Drizzle/PostgreSQL. Gunakan project database uji, bukan produksi. |
| `SESSION_SECRET` | Wajib untuk penandatanganan token sesi. |
| `PIN_PEPPER` | Wajib untuk hashing dan verifikasi PIN. |
| `SUPABASE_URL` | URL project Supabase untuk operasi Storage. |
| `SUPABASE_SERVICE_ROLE_KEY` | Akses server ke Storage; jangan pernah kirim ke client. |
| `GOOGLE_SA_EMAIL`, `GOOGLE_SA_PRIVATE_KEY`, `GOOGLE_DRIVE_ARCHIVE_FOLDER_ID` | Akses arsip Google Drive bila alur arsip dijalankan. |
| `CRON_SECRET` | Otorisasi endpoint cron bila endpoint tersebut digunakan. |

`.env.example` adalah titik awal, tetapi saat panduan ini ditulis ia tidak
mencantumkan `DATABASE_URL` walaupun konfigurasi database mewajibkannya. Ada
juga ketidaksesuaian nama folder Drive: template memuat `GOOGLE_DRIVE_FOLDER_ID`,
sedangkan helper Drive membaca `GOOGLE_DRIVE_ARCHIVE_FOLDER_ID`. Verifikasi
nama variabel terhadap pemanggil aktual sebelum menyiapkan deployment; jangan
menyalin rahasia atau menggunakan nilai lokal tanpa memahami targetnya.

Jangan menampilkan atau mengirim isi `.env`, `.env.local`, kunci Supabase,
pepper PIN, secret sesi, atau private key ke layanan eksternal.

## Perintah kerja dan verifikasi

Dari root repository:

```bash
npm run lint
npm run typecheck
npm run build
```

Untuk schema/migrasi Drizzle, jalankan dari `apps/web` agar config dan path
schema benar:

```bash
cd apps/web
npx drizzle-kit generate
npx drizzle-kit push
```

`push` mengubah schema database: gunakan hanya database development/uji yang
telah dikonfirmasi. Jangan menjalankan migrasi atau seed pada production.
Periksa SQL migration dan dampak terlebih dahulu; migrasi production memakai
proses rilis yang disetujui tim.

Tes keamanan autentikasi sederhana tersedia di
`apps/web/lib/auth/__tests__/auth.test.ts`, tetapi root `package.json` belum
menyediakan script `test`. `TESTING.md` berisi skenario otomatis dan manual,
termasuk uji konkurensi dua akun. Jangan melaporkan kriteria manual sebagai
lulus tanpa benar-benar menjalankannya.

## Pola implementasi

### API dan autentikasi

- API terlindungi menggunakan helper `withAuth`; cek role dengan
  `requireRole` dan akses cabang dengan `requireBranchAccess` di server.
- UI yang menyembunyikan tombol bukan pengganti otorisasi server.
- Validasi input klien/server mengikuti schema Zod di `packages/shared` atau
  validator lokal yang sudah dipakai route terkait.
- Mutation request dari client mengikuti pola header `X-Requested-With`.
- Pesan error kepada pengguna harus aman dan tidak memaparkan detail database,
  Storage, Google, PIN, atau hash.

### Database dan integritas data

- Gunakan Drizzle ORM dan nama kolom/field; jangan bergantung pada urutan kolom.
- ID baru menggunakan ULID. Simpan waktu `TIMESTAMPTZ` sebagai UTC dan
  tampilkan sesuai zona waktu cabang.
- Bungkus satu aksi tulis dalam `db.transaction(...)`.
- Jangan menghapus baris: gunakan status void atau `is_active = false`.
- Perubahan schema harus append-only lewat migration baru; koordinasikan
  perubahan schema Drizzle dan kontrak Zod.
- Shift menyimpan snapshot template saat dibuka. Template yang diedit hanya
  berlaku untuk shift baru.
- BR-01: partial unique index dan PostgreSQL advisory lock; jika lock gagal,
  tutup operasi dengan aman.
- BR-12: gunakan pola row lock/transaction agar aksi pertama pada item menang.
- Aksi checklist membawa `client_action_id` untuk idempotency.
- Audit log append-only; mutation sensitif ditulis bersama perubahan terkait.

### Cache dan data operasional

Ikuti pola API/client yang sudah ada dan bedakan data baca dari mutation.
Jangan menambahkan cache untuk data yang perlu diperiksa segar tanpa memahami
isolasi pengguna/cabang, `Cache-Control`, invalidasi setelah mutation, dan
frekuensi polling. Progress shift memiliki polling client; hindari memicu
request paralel berulang dari interval, focus, visibility, dan callback aksi.

## Fitur yang tampak pada implementasi saat ini

- Login username + PIN enam angka, cookie sesi, dan validasi sesi server.
- Beranda petugas dengan daftar cabang/shift yang dapat diakses.
- Buka/gabung shift, checklist bersama, progress dan peserta, serta penutupan
  shift oleh PJ dengan PIN.
- Incident: daftar, pembuatan dengan foto, detail dan catatan lanjutan.
- Laporan shift dan halaman laporan publik `/r/[token]`.
- Panel admin untuk cabang, akun, shift/template, kategori incident, laporan,
  pengaturan, dan audit log.
- Navigasi petugas menggunakan bottom bar di mobile serta menu hamburger
  desktop pada layar yang memasang `PetugasNav`.

Tabel di atas adalah orientasi, bukan jaminan bahwa seluruh perilaku PRD sudah
selesai. Periksa setiap route dan jalankan pengujian terkait sebelum
memperluasnya.

## Hal yang perlu diverifikasi oleh developer berikutnya

Ini adalah catatan implementasi untuk diteliti, bukan keputusan produk:

1. **Paksa ganti PIN:** route `/ganti-pin` tersedia, tetapi verifikasi bahwa
   login dengan `mustChangePin` benar-benar mengarahkan dan membatasi pengguna
   ke alur tersebut sebelum menyatakan kebijakan ini ditegakkan.
2. **Environment template:** selaraskan `.env.example` dengan variabel yang
   dibaca runtime (lihat tabel setup), tanpa pernah menambahkan nilai secret.
3. **Polling progress:** ukur endpoint `/api/shifts/[id]/progress` dengan
   beberapa client. Pastikan fokus/visibility/interval dan refresh setelah aksi
   tidak menumpuk request.
4. **Uji lintas role/cabang:** uji akses API langsung, bukan hanya tampilan UI.
   Uji aksi bersamaan BR-01 dan BR-12 memakai dua akun/permintaan paralel.
5. **Kesesuaian spesifikasi:** bandingkan fitur yang akan dikerjakan dengan
   status di `IMPLEMENTATION_PLAN.md`, kode saat ini, dan `TESTING.md`.

Jangan menambahkan dependency, route, atau fitur produk yang tidak diminta.
Untuk keputusan terbuka (misalnya pilihan UX yang ditandai di `APP_FLOW.md`),
mintalah keputusan sebelum implementasi.

## Checklist sebelum mengirim perubahan

- [ ] Baca aturan `AGENTS.md` dan spesifikasi relevan.
- [ ] Batasi perubahan pada satu fase/tujuan; sebutkan asumsi dan file yang
  disentuh sebelum implementasi.
- [ ] Pertahankan perubahan lokal yang sudah ada; jangan menghapus atau
  meng-commit pekerjaan lain.
- [ ] Jalankan lint, typecheck, build, dan tes paling kecil yang mencakup
  perubahan.
- [ ] Jalankan pemeriksaan manual yang diwajibkan di `TESTING.md`.
- [ ] Pastikan tidak ada rahasia, PIN, atau hash PIN di source/log/response.
- [ ] Laporkan apa yang diubah, apa yang benar-benar diuji, dan apa yang belum
  diverifikasi.
